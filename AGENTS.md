# Arcadia development instructions

## Project identity

- This repository is **Arcadia**, an SS13 project built with BYOND and Dream Maker (DM) on a `/tg/station`-derived codebase.
- Names such as `tgstation.dme`, `tgstation.dmb`, and upstream documentation are technical inheritance, not the product identity.
- This is not SS14, RobustToolbox, Unity, Unreal, Godot, or an `_NC` project. Do not apply their architecture, create `_NC` directories, or add Astro/PolyForm headers.
- Do not introduce a new downstream namespace or repository-wide folder convention without explicit user approval.

## Sources of truth

Use this order when guidance conflicts:

1. The user's current request and approved plan.
2. The closest applicable `AGENTS.md` or `AGENTS.override.md`.
3. Existing Arcadia behavior and conventions in the affected system.
4. Local repository guides and documentation.
5. Upstream patterns that do not conflict with Arcadia.

An upstream implementation is evidence, not authorization to port, rename, or redesign working Arcadia behavior.

## Mandatory architecture gate

Before editing game code, maps, schemas, interfaces, configuration, or assets:

1. Identify the involved types, procs, subsystems, files, and generated artifacts.
2. Explain the intended implementation and validation.
3. Identify compatibility, lifecycle, performance, security, map, schema, and downstream-conflict risks.
4. Wait for the user's `go`, `approved`, or equivalent approval.

Approval applies only to the proposed scope. Stop for approval if implementation discovers a materially different design or expands into additional systems. Read-only investigation and planning do not need approval. After approval, carry routine implementation and validation through to completion without repeatedly asking.

## Working discipline

- Start with `git status --short --branch`. Preserve every pre-existing change and never fold unrelated work into the task.
- Search with `rg` and `rg --files`. Trace definitions, parents, overrides, callers, signals, consumers, and tests before adding an API.
- Prefer an existing helper, component, element, subsystem, trait, callback, or signal over parallel infrastructure.
- Keep changes atomic and topical. Do not combine balance, feature, refactor, cleanup, or formatting work without an approved dependency.
- Patch surgically. Avoid whole-file rewrites and unrelated reformatting.
- Preserve LF line endings. Follow `.editorconfig`; DM code uses tabs.
- Put code beside the system it extends. Do not create a generic Arcadia dumping directory.
- Comment intent, invariants, ownership, security boundaries, and non-obvious performance behavior. Do not narrate self-evident code.

## DM and BYOND invariants

- Follow `.github/guides/STYLE.md` and `.github/guides/STANDARDS.md`.
- Use absolute leading-slash type/proc paths and snake_case identifiers. Do not use nested relative definitions or text type paths.
- Prefer `Initialize()` over `New()` for atoms and preserve parent-call/init-hint contracts.
- Clean owned references and registrations in `Destroy()`, then return the parent result. Cleanup must not introduce unrelated gameplay effects.
- Use `qdel()` and QDEL helpers instead of direct `del`. Choose ownership, strong references, weakrefs, and deletion signals deliberately.
- Signal callbacks use the appropriate `PROC_REF` macro, begin with `SIGNAL_HANDLER`, do not sleep, and unregister when observation ends.
- Use components for reusable per-parent state and elements for lightweight shared behavior. Respect duplicate, compatibility, transfer, attach, and detach contracts.
- Use source-aware traits instead of ad-hoc booleans when the condition is already modeled as a trait.
- Processing must be frame-independent and use `seconds_per_tick`. Use `SSmove_manager` instead of BYOND `walk*()` procs.
- Never hide a global scan, repeated icon construction, blocking input, sleep, or large allocation inside a hot proc, signal handler, verb, or subsystem fire loop.
- Treat player input, Topic/href values, TGUI params, refs, and delayed prompt results as hostile. Validate authority and state on the server before and after asynchronous input.

## Generated and structured files

- `tgstation.dme` and `code/modules/unit_tests/_unit_tests.dm` have tool-enforced include regions. Keep them sorted and avoid unrelated reordering.
- Edit source `.bt.json`, never compiled behavior-tree JSON under `build/behavior_trees`.
- Use TGM-compatible map tooling. Map-affecting mass type-path changes must use `tools/UpdatePaths`.
- Determine whether an icon is generated by icon cutter before editing DMI/PNG files.
- Keep database schemas, SQL changelog entries, and schema-version defines synchronized.
- Treat distributed `config/` as a compatibility surface because deployed configuration is user-owned.

## Validation

Choose the smallest checks that catch realistic regressions, then expand with risk:

- Full Windows build: `BUILD.cmd`.
- Targeted DM build: `tools\build\build.bat dm`.
- DM test run: `tools\build\build.bat dm-test`.
- TGUI checks: `tools\build\build.bat tgui-lint tgui-test`.
- Full build/test/lint: `tools\build\build.bat all` when warranted.
- Always inspect the final diff and run `git diff --check`.

Compilation alone does not prove gameplay behavior. Add or update focused tests where practical, exercise relevant map/UI behavior, and report checks that could not run.

## Licensing and attribution

- Preserve repository AGPLv3/GPL history and file-local licensing. Do not add incompatible headers.
- Verify asset provenance and exceptions before relying on the repository's stated CC BY-SA coverage.
- Ports and third-party code, sprites, sounds, or tools require compatible licensing and clear attribution.
- Do not copy material of uncertain origin.

## Project skills

Use the matching project skill whenever a task enters its scope:

- `arcadia-repository-navigation`: repository ownership, dependencies, generated files, and change placement.
- `arcadia-dm-core`: general DM code, APIs, atoms, datums, defines, helpers, and secure interactions.
- `arcadia-dcs-lifecycle`: signals, components, elements, traits, references, initialization, deletion, and GC.
- `arcadia-subsystems-performance`: subsystems, processing, timers, movement loops, spatial work, and hot paths.
- `arcadia-testing-ci`: DM/TGUI tests, builds, linters, include checks, and CI diagnosis.
- `arcadia-tgui`: TGUI interfaces and their DM backends.
- `arcadia-mapping-assets`: maps, map paths, DMI/PNG assets, icon cutter, overlays, and rendering.
- `arcadia-ai-behavior`: AI controllers, blackboards, behavior trees, targeting, and movement.
- `arcadia-sql-config`: database queries, schemas, migrations, configuration, and policy configuration.

Skills contain task-specific procedure; this file is the always-on Arcadia contract.
